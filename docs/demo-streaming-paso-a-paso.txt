DEMO EN VIVO - STREAMING DEL PIPELINE - PASO A PASO
===================================================

Para mostrar que el pipeline procesa statement por statement sin cargar el fuente en
memoria. Ya esta corrido: los numeros del paso 5 son medidos, no estimados.

Todo lo generado va a build/, que esta en .gitignore. OJO: './gradlew clean' borra
build/ y te lleva el fuente grande y el .patch. Si vas a hacer la demo, no corras clean
antes (o regenera).

PASO 1 - GENERAR EL FUENTE (~10 s)
----------------------------------

Guardar como Gen.java en cualquier carpeta temporal:

--------------------------------------------------------------------------------
import java.io.*;
import java.nio.file.*;

public class Gen {
    public static void main(String[] args) throws Exception {
        Path out = Path.of(args[0]);
        long targetBytes = Long.parseLong(args[1]) * 1024L * 1024L;

        // pocas variables declaradas una sola vez: la symbol table y el environment
        // quedan chicos, asi que lo unico que puede crecer es el fuente.
        String header =
            "let a: number = 1;\n"
            + "let b: number = 2;\n"
            + "let texto: string = \"arranca\";\n"
            + "println(texto);\n";
        String block = "a = b + 1;\nb = a - 1;\n";   // valores estables, 22 bytes

        StringBuilder chunk = new StringBuilder();
        while (chunk.length() < 1 << 20) chunk.append(block);
        String chunkStr = chunk.toString();

        long written = 0;
        int statements = 4;
        try (BufferedWriter w = Files.newBufferedWriter(out)) {
            w.write(header);
            written += header.length();
            while (written < targetBytes) {
                w.write(chunkStr);
                written += chunkStr.length();
                statements += (chunkStr.length() / block.length()) * 2;
            }
        }
        System.out.println("bytes=" + Files.size(out) + " statements=" + statements);
    }
}
--------------------------------------------------------------------------------

Correr, desde la raiz del repo:

    java <carpeta>/Gen.java build/fuente-grande.ps 50
    java <carpeta>/Gen.java build/fuente-enorme.ps 200

    -> bytes=52429385  statements=4766304
    -> bytes=209717285 statements=19065204

(el de 200 MB es opcional, es el que hace efecto)

Por que el fuente declara 3 variables y repite asignaciones, en vez de un 'let' distinto
por linea: semantic (SymbolTable) e interpreter (Environment) guardan una entrada por
variable DISTINTA. Eso es inherente a cualquier type checker, no es un leak, pero con
millones de nombres unicos la memoria crece por la tabla de simbolos y la prueba mide
otra cosa. Con 3 variables, lo unico que crece es el archivo.


PASO 2 - ARMAR EL CLASSPATH (una sola vez por sesion)
-----------------------------------------------------

:cli no tiene el plugin 'application', asi que la task ':cli:run' NO existe. Para poder
pasarle un -Xmx explicito hay que llamar a java directo.

Guardar como printcp.gradle en una carpeta temporal:

    allprojects {
        plugins.withId('java') {
            tasks.register('printRuntimeClasspath') {
                doLast { println sourceSets.main.runtimeClasspath.asPath }
            }
        }
    }

Y despues, desde la raiz del repo:

    ./gradlew :cli:assemble
    CP=$(./gradlew -I <carpeta>/printcp.gradle :cli:printRuntimeClasspath -q --console=plain | tail -1)
    echo "$CP" | head -c 200      # chequeo rapido de que quedo algo

El -Xmx es el punto de todo el ejercicio. Con heap default (1/4 de la RAM) la prueba no
dice nada: 50 MB entran en memoria sin esfuerzo.

PASO 6 - EL ERROR TARDIO (el trade-off del ADR 0002)
----------------------------------------------------

    printf 'let a: string = "linea 1";\nprintln(a);\nlet b: string = "linea 2";\nprintln(b);\nlet c: number = "esto no es un number";\nprintln(c);\n' > build/error-tardio.ps

    java -cp "$CP" printscript.cli.MainKt Execution build/error-tardio.ps
        linea 1
        linea 2
        Error Semantic: Incompatible types.

    java -cp "$CP" printscript.cli.MainKt Validation build/error-tardio.ps
        Incompatible types.

Execution ya imprimio dos lineas cuando se entera del error, y eso NO se puede evitar sin
materializar el fuente — que es exactamente lo que la consigna prohibe. Validation
recorre el mismo pipeline sin efectos y lo reporta limpio. Ese es el mitigante, y es todo
el contenido del ADR 0002.


QUE ES EL HOTFIX (y que NO arregla)
-----------------------------------

Todo en cli/src/main/kotlin/printscript/cli/Main.kt. El pipeline (lexer, parser,
semantic, interpreter) ya era lazy; el CLI era el unico que lo alimentaba con el archivo
entero cargado. Son dos cambios:

  a) Sacar el readText() y pasarle el Reader al Engine, que ya tenia el overload:

        - val code = File(filePath).readText()
        - executePrintScript(code)
        + val result = File(filePath).reader().use { engine.execute(it) }

  b) Sacar el .toList() de parseToAST y devolver un Iterator<Statement>. Con eso
     Validation tambien pasa a ser streaming.

Formatting y Analyzing NO se arreglan con esto: Formatter.format() recibe una List, asi
que ahi hay que materializar hasta que cambien las firmas de formatter/linter (PR 0 de
Dev 3). Quedaron materializando a proposito, con un comentario que dice por que.
